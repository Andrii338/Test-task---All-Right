## Рішення під час реалізації

- Один runner для UI й API, щоб мати спільні fixtures, звіт і CI без другого фреймворку.
- Реалізовано 6 основних і 3 негативні UI-тести. В одному тесті перевіряються всі чотири сортування; в іншому — три обов’язкові поля чекауту.
- API lifecycle оформлено одним тестом із `test.step`: auth, create, read, update, read, delete, read 404. Три негативні тести незалежні від нього.
- При перевірці документації підтверджено специфічні HTTP-коди: create 200 і delete 201. Вони не замінені типовими REST-припущеннями 201 і 204.
- API fixture реєструє створений ID до перевірки вмісту відповіді, щоб assertion failure не пропустив cleanup. Унікальний `lastname` використовується як маркер власності й перевіряється перед видаленням.
- Відомий UI-дефект винесено в окремий project. `test.fail` застосовано після успішного setup і переходу, щоб не приховувати помилки запуску браузера.
- Необов’язковий генератор тестів через модельний API не включений в основний обсяг.

## Три реальні помилки агента

### 1 Використав стандартний npm cache поза доступною директорією

**Що зробив:** виконав `npm view @playwright/test version` без окремого cache.

**Як помітив:** команда завершилася `EPERM` на `~/.npm/_cacache/tmp/...`. npm запропонував зміну власника cache, але в цій сесії запис у домашній cache обмежений sandbox-ом.

**Що виправив:** повторив запити й установлення з `npm --cache ../../work/npm-cache ...` у робочій директорії. Права домашньої директорії не змінював.

**Перевірка:** залежності встановлено успішно; створено lockfile; TypeScript компілюється. Це помилка підготовки середовища агентом, а не дефект тестованого продукту.

### 2 Запустив UI runner до встановлення відповідного Chromium

**Що зробив:** після встановлення npm-пакетів виконав `npm test`, не завершивши встановлення браузера потрібної версії. У системі були інші ревізії Playwright Chromium.

**Як помітив:** 4 API-тести пройшли, 9 UI-тестів упали за 1–2 мс із `Executable doesn't exist ... chromium_headless_shell-1255` ще до відкриття сайту. [Стислий результат першого запуску](docs/evidence/initial-run.json).

**Що виправив:** установив Chromium, headless shell і ffmpeg у task-local cache; README містить крок установлення, CI встановлює браузер перед тестами.

**Перевірка:** повторний запуск знайшов executable. Він виявив інший, незалежний блокер sandbox macOS — `bootstrap_check_in ... Permission denied (1100)`. Встановлення браузера виправило початкову помилку, але не зняло системне обмеження. Це явно відокремлено від результатів тестів.

### 3 Початкова перевірка зображень перевіряла тільки видимість

**Що зробив:** у першій версії UI-02 використав лише `expect(image).toBeVisible()`.

**Як помітив:** під час перегляду асертів встановив, що видимий `<img>` може мати незавантажений або зламаний ресурс; така перевірка не доводить готовність зображення.

**Що виправив:** додав `expect.poll` на `image.complete && image.naturalWidth > 0`. Тест має впасти для видимого, але зламаного зображення.

**Перевірка:** TypeScript приймає перевірку; браузерне читання DOM підтвердило `imageLoaded: true` у всіх шести реальних товарів. Повний UI runner перевіряється окремо через CI. Це недолік першої реалізації, знайдений під час review, а не твердження про навмисно внесений баг.

## Що перевірити перед здачею

Після публікації дочекатися завершення workflow, переглянути фактичний підсумок і наявність звіту. Зелене завершення з expected failure означає, що відомий дефект досі відтворюється, а не що продукт пройшов цю перевірку. Не видавати локальний sandbox failure або браузерний огляд за повний успішний UI-прогін.
